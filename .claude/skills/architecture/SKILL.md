# Architecture and patterns

## 1. Modular monolith
- .NET 9, PostgreSQL, EF Core (Entity Framework Core), JWT (JSON Web Token) auth, Sentry
- Modules: `Modules.Identity`, `Modules.Menu`, `Modules.Organization`, plus `Shared` and `Web`
- Modules never reference each other; they share only through `RestaurantManagement.Shared`
- `Web` is the host: it registers the modules; each module owns its own controllers
- Each module has its own `CLAUDE.md` with module-specific rules. Read it for every module you touch

## 2. Cross-module access
- Never inject another module's DbContext, services or entities
- The owning module exposes an interface in Shared (e.g. `IOrganizationLookup`), implements it
  internally, and the Web host registers it
- Contracts return simple DTOs (Data Transfer Objects), never entities
- Store other modules' data as IDs only (e.g. `OrganizationId`); no cross-module foreign keys or joins
- Existing code that injects other modules' DbContexts is legacy: don't copy the pattern;
  flag it instead of refactoring unless the task asks for it

## 3. Multi-tenancy and roles
- Data belongs to an organization; always scope queries by `OrganizationId`
- Roles: Owner, Admin, Manager, Cashier, Waiter, Kitchen (fixed, in code). Access is decided by
  **permissions** through the authorization policies, never by checking a role name in code. A user
  can hold several role assignments, per location or for all locations of an organization

## 4. Module folders
Every module uses the same folders:

| Folder | Holds |
|---|---|
| `Controllers/` | HTTP only: bind input, call a service, return the response. No business logic |
| `Services/` | Business rules and use cases |
| `Data/` | The module's DbContext and database configuration |
| `Entities/` | Database entities; never returned from controllers |
| `Models/` | Request and response DTOs; controllers accept and return these only |
| `Migrations/` | Generated by EF Core; never edit by hand, except adding `migrationBuilder.Sql` data backfills, which must be flagged in the plan. Follow `.claude/skills/ef-migration/SKILL.md` |

## 5. Rules
- Each module has its own DbContext; never query another module's tables
- Services use the module's DbContext directly; no repository layer
- Map entities to response models with a private static `MapToResponse` method in the service; no AutoMapper
- Not found: return `null` (or `false` for deletes); the controller turns that into 404
- One responsibility per class; if a class does two jobs, split it
- SOLID (Single responsibility, Open/closed, Liskov substitution, Interface segregation,
  Dependency inversion): services depend on interfaces; cross-module contracts stay small
