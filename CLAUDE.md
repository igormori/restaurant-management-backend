# RestaurantManagement

## Architecture
- .NET 9, PostgreSQL, EF Core, JWT auth, Sentry
- Modular monolith: Modules.Identity, Modules.Menu, Modules.Organization, Shared, Web
- Modules never reference each other; share only through RestaurantManagement.Shared
- Cross-module access:
  - Never inject another module's DbContext, services, or entities
  - The owning module exposes an interface in Shared (e.g. `IOrganizationLookup`),
    implements it internally, and the Web host registers it
  - Contracts return simple DTOs, never entities
  - Store other modules' data as IDs only (e.g. `OrganizationId`); no cross-module foreign keys or joins
  - Existing code that injects other modules' DbContexts is legacy: don't copy the pattern;
    flag it instead of refactoring unless the task asks for it
- Web is the host: it registers the modules; each module owns its own controllers
- Multi-tenant: data belongs to an organization; always scope queries by OrganizationId
- Roles: Owner, Admin, Staff

## Commands
- Build: `dotnet build RestaurantManagement.sln`
- Test: `dotnet test`
- Format: `dotnet format`
- Run: `dotnet run --project src/RestaurantManagement.Web` (Swagger at /swagger)
- New migration:
  `dotnet ef migrations add <Name> --project src/RestaurantManagement.Modules.<Module> --startup-project src/RestaurantManagement.Web --context <Module>DbContext`
- Build and tests must pass before a task is done
- Never commit secrets (connection strings, JWT key)

## Separation of concerns
Every module uses the same folders:
- `Controllers/` HTTP only: bind input, call a service, return the response. No business logic
- `Services/` business rules and use cases
- `Data/` the module's DbContext and database configuration
- `Entities/` database entities; never returned from controllers
- `Models/` request and response DTOs; controllers accept and return these only
- `Migrations/` generated by EF Core; never edit by hand

Rules:
- Each module has its own DbContext; never query another module's tables
- Services use the module's DbContext directly; no repository layer
- Map entities to response models with a private static `MapToResponse` method in the service; no AutoMapper
- Not found: return `null` (or `false` for deletes); the controller turns that into 404
- One responsibility per class; if a class does two jobs, split it

## Clean code
- Clarity over cleverness: code should read like a description of what it does
- Guard clauses first: handle invalid and failure cases at the top and return early,
  then write the happy path without nesting

  ```csharp
  if (request is null) return Error("Request is required");
  if (!organization.IsActive) return Error("Cannot add items to an inactive organization");

  // happy path
  ```

- Avoid `else` after a `return`; keep nesting to 2 levels max
- Small methods with intention-revealing names
- No magic strings or numbers; use named constants
- Comments explain why, not what; no commented-out code
- Async all the way; never `.Result` or `.Wait()`
- Constructor injection into `private readonly` fields
- Models are classes with `{ get; set; }` properties, matching the existing Models folders

## Testing standards
- xUnit, FluentAssertions, NSubstitute for mocks
- Integration tests: WebApplicationFactory + Testcontainers for a real database
- Test projects mirror src: `tests/<ProjectName>.Tests`
- Arrange / Act / Assert, one behavior per test
- Test names: `Method_Scenario_ExpectedResult`
- Cover the failure cases first, then the happy path
- Bug fixes start with a failing test that reproduces the bug

## How to work
- State assumptions. If something is ambiguous, ask in chat; in a subagent or CI run,
  list open questions in your output instead of guessing silently
- Minimum code that solves the request: no speculative features, abstractions, or config
- Surgical changes: don't refactor or reformat code outside the task; mention issues instead
- Remove only the unused code your own change created
