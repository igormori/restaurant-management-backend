## T3 — Memberships replace role rows; token carries no roles
| Field | Value |
|---|---|
| Expected context | `user_roles` (`src/RestaurantManagement.Modules.Identity/Entities/UserRole.cs`: user, organization, optional location, role name) is both membership and access. `User.Roles` is read by `SessionService` (login, refresh rule F5, select organization), `OrganizationMembership` and `AccessTokenFactory` (role claims, identity matrix L14). `UserRoleLookup` and `UserRoleAssigner` implement the old Shared contracts that Menu, Organization and `LocationAccessMiddleware` use until T6–T9. | Expected result | Table `organization_members` (user, organization, Owner flag; one row per user and organization; organization never empty) replaces `user_roles`, which is dropped. A membership is an organization row (`TenantEntity`), so the audit interceptor refuses writing one into another organization. Login, refresh, select and the organization choices use memberships with today's rules. The access token (JWT: JSON Web Token) carries the user and the organization only, never a role claim. Until T10 the old contracts keep compiling over memberships: an Owner reads as "Owner for all locations", anyone else has no role and no location access; assigning Owner adds an Owner membership, revoking removes it |
| Outcome | #11 (no role claim after login, refresh or select), #5 (Owner is a flag, not a role), #12 (a membership in another organization never selects or refreshes into this one).
