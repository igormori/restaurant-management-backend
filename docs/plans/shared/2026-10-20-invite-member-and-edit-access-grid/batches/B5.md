## T7 — Accept an invitation
| Field | Value |
|---|---|
| Expected context | A pending invitation grants nothing: no membership, so login, organization choice (identity matrix S3) and the access guard refuse the organization. Registration creates unverified accounts that verify by code. Writing rows of an organization other than the token's needs `ITenantScope.Begin(organizationId)`, or the audit interceptor refuses them. `api/auth` actions are POST with body only (T23) and rate-limited (`AuthRateLimitPolicies`) |
| Expected result | Signed in: `POST api/invitations/accept` with the token; the signed-in account's email must equal the invited email. New account: `POST api/auth/accept-invitation` (public, `Verify` rate-limit policy) with token, first and last name and password (registration rules); the account is created verified; an existing account for that email gets 400 asking to sign in. Both: an unknown, expired, used, replaced or cancelled token gets one generic 400. On success, in one transaction under the invitation's tenant scope: a membership (never Owner), the stored levels and labels exactly as invited, the invitation marked used. Other organizations' memberships are untouched; the user then chooses the organization as usual |
