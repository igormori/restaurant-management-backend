## T1 — Audit log storage and writer
| Field | Value |
|---|---|
| Expected context | No audit log exists. Shared holds the base entities (`TenantEntity`), the audit stamping interceptor (`AuditSaveChangesInterceptor`), tenant query filters (`ApplyTenantQueryFilters`) and cross-module contracts under `Services/`. The interceptor sets the organization from the tenant scope or token and refuses another organization. Each module's DbContext is registered in `src/RestaurantManagement.Web/Program.cs` with Npgsql, snake_case names and the interceptor; follow that pattern and `.claude/skills/ef-migration/SKILL.md`. Never share a database transaction across modules, so the entry is written in its own save. There is no outbox yet (`backlog/improvements/2026-10-16-audit-entries-through-outbox.md`) |
| Expected result | Shared owns an `audit_log_entries` table through its own DbContext. An entry holds: organization, optional location, user, action, changed item (type and ID), before value, after value, optional reason, IP address and time. Organization comes only from the token or tenant scope (interceptor stamping). User and time come from the stamps (`CreatedByUserId`, `CreatedAt`). IP address comes from the current request. Actions are fixed string constants in Shared: member role changed, settings changed, location status changed. They are stored as text, so Phase 1 and task 10's `role assigned` can add actions without a migration. In this plan nothing writes `member role changed`: the feature doesn't exist yet (`backlog/features/2026-10-16-member-role-change.md`). Index on (organization, time). `IAuditLog` offers one operation: record an entry from a small DTO. Nothing can update or delete an entry: the DbContext refuses to save a changed or removed entry |
| Outcome | #4 and Rules 1–3: a recorded entry reads back with every field; an attempt to change or remove a stored entry fails and the row is unchanged |
