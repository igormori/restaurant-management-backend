## T1 — Refresh token table and entity
| Field | Value |
|---|---|
| Expected context | Today each `User` holds one `RefreshTokenHash` (BCrypt) and `RefreshTokenExpiry`. `UserVerificationCode` is the pattern to follow: a plain entity (not `BaseEntity`/`TenantEntity`) owned by the user with a cascade-delete foreign key configured in `IdentityDbContext`. The token must NOT be a `TenantEntity`: sign-in has no organization, and `AuditSaveChangesInterceptor` would reject it. Old `User` fields stay until T5 |
| Expected result | A `refresh_tokens` table exists. Each row: Id, UserId, OrganizationId (nullable, ID only, no cross-module foreign key), FamilyId, TokenHash (unique index), CreatedAt, ExpiresAt, RevokedAt (nullable), RevocationReason (nullable: rotated, logout, logout everywhere, reuse detected), ReplacedByTokenId (nullable), DeviceDescription (nullable, max 512), IpAddress (nullable, max 45). Indexes on UserId and FamilyId. Deleting a user deletes their tokens (database cascade) |
| Outcome | Foundation for #1 and #7; Rule 8 checked by deleting a user row with raw SQL on PostgreSQL and finding no tokens left |
