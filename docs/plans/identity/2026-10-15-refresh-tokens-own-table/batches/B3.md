## T3 — Sign-in, refresh and organization selection use per-device tokens in a cookie
| Field | Value |
|---|---|
| Expected context | `SessionService.LoginAsync`, `RefreshTokenAsync` and `SelectOrganizationAsync` write `User.RefreshTokenHash`/`RefreshTokenExpiry`; refresh takes `RefreshRequest` (email + token) in the body and reads `User.SelectedOrganizationId`. `AuthResponse.RefreshToken` returns the token in the body. Refresh uses a misspelled localizer key (`InvlideOrExpiredToken`) and a separate `InvalidRefreshToken` message. Login's generic 401 and dummy-hash rules in the Identity CLAUDE.md stay untouched. CORS policy has no `AllowCredentials` |
| Expected result | Login starts a new family with no OrganizationId (same as today's refresh after login: a user with one organization still gets it claimed automatically) and stores device description (User-Agent header) and IP address. Refresh reads only the cookie, rotates through `IRefreshTokenService`, and builds the access token for the token's own OrganizationId (still refused if membership was removed). Select-organization rotates the current cookie token into the same family with the chosen OrganizationId, or starts a new family when no valid cookie is sent. Every refusal (missing, unknown, expired, revoked, inactive/unverified/locked user) is the same 401 with `InvalidOrExpiredToken`. The controller sets cookie `refresh_token`: HttpOnly, Secure, SameSite=Strict, Path `/api/auth`, expiry = token expiry. Response bodies no longer contain the refresh token. CORS policy allows credentials. `User.SelectedOrganizationId` is still written as today; old `User` token fields are no longer read or written |
| Outcome | #1 cookie attributes checked on the login response and one active row exists · #2 two logins then two refreshes both succeed · #3 refresh rotates · #4 reused cookie gives 401 and family revoked · #5 expired cookie gives 401 |
| Files | `change` src/RestaurantManagement.Modules.Identity/Services/ISessionService.cs and SessionService.cs · `change` src/RestaurantManagement.Modules.Identity/Controllers/AuthController.cs · `add` cookie helper in src/RestaurantManagement.Modules.Identity/Controllers/ · `add` client info model and session result model in src/RestaurantManagement.Modules.Identity/Models/ · `change` AuthResponse.cs · `delete` RefreshRequest.cs · `change` src/RestaurantManagement.Web/Program.cs (CORS) · `change` tests that use the old fields: SessionServiceRefreshTests, SessionServiceLoginTests, SessionServiceSelectOrganizationTests, SessionServiceOrganizationClaimTests, SessionServiceVerificationTests · `add` tests/RestaurantManagement.Web.Tests/RefreshTokenCookieEndpointTests.cs |
| Modules | Identity, Web (CORS only) |
| Flags | Auth change; API contract change (token leaves the body, refresh body removed); CORS `AllowCredentials` |
| DoD | Tests written and passing · Web.Tests: login, refresh and select-organization responses set the cookie with HttpOnly, Secure, SameSite=Strict, Path `/api/auth`, and no token in the body · refresh without a cookie returns 401 · unit tests: failure cases first, two devices, rotation, reuse, expiry, per-token organization survives another device selecting a different organization · a token of a user in another organization cannot refresh into an organization they are not a member of (401) · no role restriction (spec allows all roles) |
| Depends on | T2 |
| Uses from dependency | `IRefreshTokenService` issue and rotate |
| Provides | Cookie helper and client info capture used by T4 |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | In `ISessionService`/`SessionService`, delete the old `LoginAsync(LoginRequest)`, `RefreshTokenAsync(RefreshRequest)` and `SelectOrganizationAsync(Guid, SelectOrganizationRequest)` and the 6-parameter constructor; implement the stubbed replacements and keep the 7-parameter constructor (it adds `IRefreshTokenService`) |
| 2 | Login: unchanged password, lockout and generic-401 rules; issue a token only after every check has passed (#41, #71–#73); then issue a new family with no organization and the device info, return `SessionResult` (body in `Auth`, token and expiry beside it). Stop writing `User.RefreshTokenHash`/`RefreshTokenExpiry` |
| 3 | Refresh, in this order: missing token → 401 `InvalidOrExpiredToken`; rotate; `null` → same 401; load the user of the rotated token and apply the active/verified/locked gates and the membership check for the token's own organization; on any refusal revoke the replacement just issued, then throw the same 401 (scenario #74: no active token left behind); otherwise build the access pass for that organization |
| 4 | Select organization: keep today's checks (400/403/401); rotate the cookie token into the chosen organization passing the caller's ID as `expectedUserId`; when that returns `null` (no cookie, expired, revoked, or another user's token) issue a new family for the caller. Keep writing `User.SelectedOrganizationId` |
| 5 | Remove `AuthResponse.RefreshToken`, delete `RefreshRequest.cs`, drop the misspelled `InvlideOrExpiredToken` and the `InvalidRefreshToken` uses |
| 6 | Controller: read the `refresh_token` cookie, build `ClientInfo` from the User-Agent header and the connection's remote IP, call the service, write the cookie through a small helper (HttpOnly, Secure, SameSite=Strict, Path `/api/auth`, Expires = token expiry), return `result.Auth`. Refresh takes no body |
| 7 | `Program.cs`: add `AllowCredentials()` to the CORS policy |

- **Tests to make pass, in order:** #27–#35, #74, #41, #71–#73, #36–#40, #42–#45, #70, then Web #46–#52; then the moved existing tests listed in scenarios.md (login, claim, select-organization, verification, uniform response, rate limiting)
- **Stubs created:** `Models/ClientInfo.cs` — device description and IP; `Models/SessionResult.cs` — body plus token and expiry for the cookie; stubbed methods and the extra constructor in `Services/ISessionService.cs` and `Services/SessionService.cs`
- **Follow this existing pattern:** current `SessionService` gates and `GenerateJwt`; `AuthController.SelectOrganization` for reading the user ID from claims
- **Watch out for:** never rotate or revoke a cookie token that belongs to someone other than the caller (scenario #70). Keep the dummy-hash login rule (Identity CLAUDE.md). No role restriction on any of these endpoints. `RefreshTokenAsync(null)` is ambiguous only while the old overload exists; tests pass a typed null

## T4 — Logout (this device) and sign out everywhere endpoints
| Field | Value |
|---|---|
| Expected context | No logout exists. Cookie helper and client info come from T3. `[Authorize]` endpoints read the user ID from `ClaimTypes.NameIdentifier`, as `SelectOrganization` does |
| Expected result | `POST api/auth/logout` (public, Refresh rate-limit policy) revokes only the cookie's token, clears the cookie and returns 204 whether or not the token was valid. `POST api/auth/logout-all` (`[Authorize]`) revokes every token of the caller, clears the cookie and returns 204 |
| Outcome | #6 two devices, logout on one: only that row revoked, the other device still refreshes · #8 logout-all: no active token left for the caller |
| Files | `change` ISessionService.cs, SessionService.cs, AuthController.cs · `add` tests/RestaurantManagement.Modules.Identity.Tests/SessionServiceLogoutTests.cs · `add` tests/RestaurantManagement.Web.Tests/LogoutEndpointTests.cs |
| Modules | Identity |
| Flags | New public endpoint (logout); new authenticated endpoint (logout-all) |
| DoD | Tests written and passing · logout with unknown or missing cookie returns 204 and changes nothing · logout-all without an access token returns 401 · cross-tenant: logout-all by a user of organization A leaves tokens of a user of organization B active; logout with B's cookie never touches A's other tokens · responses clear the cookie · each role (Owner, Admin, Staff) may call both (spec disallows none) |
| Depends on | T3 |
| Uses from dependency | Cookie helper, client info, `IRefreshTokenService` revoke one / revoke all |
| Provides | — |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | Implement the stubbed `SessionService.LogoutAsync(token)`: no token → return; otherwise revoke that one token through `IRefreshTokenService.RevokeAsync`; an already replaced token revokes its family (handled by the service, #76); never throw for unknown or revoked tokens |
| 2 | Implement `LogoutAllAsync(userId)` with `RevokeAllForUserAsync` |
| 3 | Controller: `POST api/auth/logout` (no `[Authorize]`, `Refresh` rate-limit policy) reads the cookie, calls logout, clears the cookie, returns 204. `POST api/auth/logout-all` (`[Authorize]`) reads the user ID from `ClaimTypes.NameIdentifier`, calls logout-all, clears the cookie, returns 204 |
| 4 | Clearing the cookie uses the T3 helper with the same name and path `/api/auth` and an expiry in the past |

- **Tests to make pass, in order:** #53, #54, #76, #55–#59, then Web #60–#66, #77
- **Stubs created:** `LogoutAsync` and `LogoutAllAsync` in `Services/ISessionService.cs` and `Services/SessionService.cs`
- **Follow this existing pattern:** `AuthController.SelectOrganization` (claims → user ID, `Unauthorized()` when missing)
- **Watch out for:** the user ID for logout-all comes only from the access pass, never from the body. Logout is public by plan (flagged); it must answer 204 the same way whether or not the token was valid
