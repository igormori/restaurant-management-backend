## T2 — Refresh token service: issue, rotate, reuse detection, revoke
| Field | Value |
|---|---|
| Expected context | `SessionService` currently generates 64 random bytes with `RandomNumberGenerator` and stores a BCrypt hash on `User`; lookup is by email. Services use `IdentityDbContext` directly (no repository). One responsibility per class, so token lifecycle lives in its own service behind an interface. `SessionService` is not changed in this task |
| Expected result | `IRefreshTokenService` / `RefreshTokenService` offers: start a new family for a user (optional OrganizationId, device description, IP address) and return the raw token plus expiry; rotate a presented token (optionally into a new OrganizationId); revoke one presented token; revoke every token of a user. Fingerprint = SHA-256 (Secure Hash Algorithm, 256-bit) of the raw token, stored as hex; lookup is a direct match on TokenHash. Expiry = now + `JwtOptions.RefreshTokenExpireDays` on issue and on every rotation. Rotation marks the old row revoked (reason rotated, ReplacedByTokenId set) and adds a new row in the same family. Presenting a revoked token revokes every active token in its family (reason reuse detected) and is refused. Expired or unknown tokens are refused without changing data. Revoking the old row on rotation is a conditional update (only if still active), so a second parallel use counts as reuse. Registered in src/RestaurantManagement.Web/Program.cs |
| Outcome | #2 two families for one user rotate independently · #3 old row revoked, new row active with the same FamilyId · #4 reuse refused and whole family revoked · #5 expired token refused · #7 stored TokenHash differs from the raw token · #8 revoke-all leaves no active token for that user |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | Implement the stub `Services/RefreshTokenService.cs` behind the existing `IRefreshTokenService` stub. Keep the constructor `(IdentityDbContext, IOptions<JwtOptions>)`: tests build it directly |
| 2 | Issue: random token from `RandomNumberGenerator`, fingerprint = SHA-256 (Secure Hash Algorithm, 256-bit) of the token as hex, new `FamilyId`, expiry = now + `RefreshTokenExpireDays`, device description cut to 512 characters. Return `IssuedRefreshToken` |
| 3 | Rotate: look up by fingerprint. Unknown or expired → `null`, no change. Already revoked → revoke every still-active token of the family with reason `reuse_detected`, return `null`. When `expectedUserId` is given and the token belongs to someone else → `null`, token untouched. Active → in one transaction, conditional update (only if still not revoked) to set `RevokedAt`, reason `rotated`, `ReplacedByTokenId`, then add the replacement in the same family (organization = the chosen one, or the old one when none is given). If the conditional update changed no row, treat it as reuse |
| 4 | Revoke one (reason `logout`; returns false when unknown; an already revoked token counts as reuse: revoke the family as `reuse_detected` and return false) and revoke all for a user (reason `logout_everywhere`, only that user's active rows, returns the count) |
| 5 | Register `IRefreshTokenService` → `RefreshTokenService` as scoped in `src/RestaurantManagement.Web/Program.cs` |
