## T3 — Processor sends reset emails and retries failures
| Field | Value |
|---|---|
| Expected context | The rules that left the request in T2 (eligibility, 60 s wait, reset lock, invalidate older codes, 6-digit code from `RandomNumberGenerator`, store only `CodeHash`, logs never hold the code or email) must keep working (spec Rule 4). Follow the `RefreshTokenCleanupService` pattern: a scoped service with one method that does one pass |
| Expected result | One pass handles every due, unclaimed row: claims it with a conditional update; looks up the user; for an unknown, inactive, unverified or reset-locked account, or one within the 60 s wait, deletes the row without sending. Otherwise it creates the code as today, sends the email, and deletes the row. A send failure keeps the row, adds one attempt and sets the next attempt time growing per failure (1, 2, 4, 8 min); a retry gets a new code, so only the newest works. After the 5th failed attempt the row is marked failed and kept, and an error is logged with the row id only |
| Outcome | #3: a failed send is sent on a later pass. #4: an eligible email gets exactly one email and its code resets the password. #5: unknown, inactive and unverified emails cause no email |
| Files | `add` `src/RestaurantManagement.Modules.Identity/Services/IPasswordResetEmailProcessor.cs` and `PasswordResetEmailProcessor.cs` · `change` `src/RestaurantManagement.Modules.Identity/Services/PasswordResetService.cs` (remove moved code) · `change` `src/RestaurantManagement.Web/Program.cs` (register the processor) · `change` `src/RestaurantManagement.Modules.Identity/CLAUDE.md` (one line on the queue) · tests in both Identity test folders · `change` `docs/security/identity-matrix.md` |
| Modules | Identity (one registration line in the Web host) |
| Flags | Codes created and emails sent outside a request; claim by conditional update, no raw SQL |
| DoD | Tests written and passing · unit tests (SQLite): P1–P4 cases now proved by the processor; failed send retried and sent on the next due pass; no retry before the next attempt time; 5th failure marks the row failed with no code or email in the logs; a claimed row is skipped by a second pass · endpoint test: forgot password, one processor pass, the emailed code resets the password · P1–P5 rows changed and new P rows for retry and claim in `docs/security/identity-matrix.md`, all ✅; `python3 .claude/scripts/check-security-matrices.py` passes |
| Depends on | T1, T2 |
| Uses from dependency | Queue table (T1); rows written by the request (T2) |
| Provides | `IPasswordResetEmailProcessor` with a one-pass method, for T4 |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | Implement `PasswordResetEmailProcessor.ProcessDueAsync(utcNow, ct)` (stub, constructor already fixed: db, security options, email service, code hasher, logger). Pick due rows: `FailedAt` null, `NextAttemptAt <= utcNow`, `ClaimedUntil` null or `<= utcNow`, oldest `CreatedAt` first |
| 2 | Claim each row with a conditional `ExecuteUpdate` (set `ClaimedUntil` a few minutes ahead where the row is still unclaimed); skip it when no row was updated |
| 3 | Per row, move the old request logic here: look up the user by exact email; unknown, inactive, unverified or reset-locked gives delete the row, no email. Within `ResendCooldownSeconds` of the newest code (measured against `utcNow`) gives delete the row, no email. Otherwise invalidate unused codes, reset `PasswordResetFailedAttempts`, store the new code hash with the expiry, save, send the email, delete the row |
| 4 | On a send failure: `Attempts + 1`, `NextAttemptAt = utcNow + 2^(attempts-1) minutes` (1, 2, 4, 8), clear `ClaimedUntil`; on the 5th failure set `FailedAt` and log an error with the row id only. Never log the code, the email or the exception message (log the exception type at most) |
| 5 | Register `IPasswordResetEmailProcessor` as scoped in `Program.cs`; add the one-line note on the queue to the Identity `CLAUDE.md` |
| 6 | Set rows P2, P3, P4, P15 to P19 and P21 to ✅ in the matrix |

- **Tests to make pass, in order:** scenarios 8, 9, 10, 11, 12, 13, 21, 14, 15, 16, 17, 18, 19, 20, 22 (all in `PasswordResetEmailProcessorTests`, plus endpoint `ForgotPassword_ThenProcessorPass_EmailsOneCodeThatResetsThePassword`)
- **Stubs created:** `Services/IPasswordResetEmailProcessor.cs` (`Task<int> ProcessDueAsync(DateTime utcNow, CancellationToken ct)`, returns rows handled) and `Services/PasswordResetEmailProcessor.cs` (throws `NotImplementedException`)
- **Follow this existing pattern:** `RefreshTokenCleanupService` (scoped, one pass); the old `RequestResetCodeAsync` body in git history for the code rules
- **Watch out for:** a retry (`Attempts > 0`) must not be blocked by the 60 s wait caused by its own earlier failed attempt's code: scenario 17 passes exactly 1 minute after a failure, so skip the wait check for rows with `Attempts > 0`. A retry gets a new code and invalidates the old one. Use `utcNow` (the parameter), never `DateTime.UtcNow`, for due, claim, backoff and wait decisions so tests control time. Several rows for the same user in one pass: the second hits the wait, so one email only (scenario 21). Do not use raw SQL. A claim lasts a few minutes (`ClaimedUntil`); a pass that crashed frees its rows when the claim runs out, so keep the due filter `ClaimedUntil` null or `<= utcNow` (no test covers this). The lookup by email must match the old behaviour (exact `u.Email == email`). Registering the processor in `Program.cs` is what first turns scenario 22 from `No service registered` into a real result

**Delivered:** `PasswordResetEmailProcessor.ProcessDueAsync` (due filter, conditional-update claim for 5 minutes, eligibility and wait rules moved from the request, new code per send, delete on success, backoff 1/2/4/8 min, failed after the 5th with id-only error log). Registered as scoped in `Program.cs`; one note added to the Identity `CLAUDE.md`. `PasswordResetService` had nothing left to remove (done in T2). Matrix rows P2, P3, P4, P15 to P19, P21 set to ✅. The row-failure logs for non-final failures are a warning with id and exception type only.

**Fix round (review Watch out 1 and 3), user decision:** each pass now takes at most 100 due rows (`BatchSize`, oldest first) and first deletes rows marked failed more than 7 days ago (`FailedRetention`). Assumptions: the 7 days count from `FailedAt`; the delete runs at the start of every pass. New tests in `PasswordResetEmailProcessorLimitsTests.cs` (scenarios 26, 27); matrix rows P22, P23.
