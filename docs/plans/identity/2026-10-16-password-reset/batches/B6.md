## T8 — Change a known password
| Field | Value |
|---|---|
| Expected context | `PasswordVerifier.Verify` checks a password against its BCrypt hash. `IRefreshTokenService` revokes all tokens of a user (reason parameter added in T7). The user is identified only by the token's subject claim, never by the request body |
| Expected result | New `PasswordChangeService` taking the user ID, current password and new password (T4 rules). Unknown, inactive or unverified user is rejected as an invalid session. Wrong current password is rejected with a clear message and nothing changes. New password equal to the current one is rejected. On success, in one Identity transaction: new hash and all refresh tokens revoked with reason `password_changed`. Then T5 records the audit entry |
| Outcome | #7, #8, #9, #11 — verified by unit tests: wrong current password leaves the hash unchanged, same password refused, weak password refused, success changes the hash, revokes every refresh token and calls the audit recorder once |
| Files | `add` `src/RestaurantManagement.Modules.Identity/Services/IPasswordChangeService.cs`, `PasswordChangeService.cs` · `add` `Models/ChangePasswordRequest.cs` · `change` `src/RestaurantManagement.Shared/Localization/SharedResource.resx`, `SharedResource.pt.resx` · `add` `tests/RestaurantManagement.Modules.Identity.Tests/PasswordChangeServiceTests.cs` |
| Modules | Identity (plus resource keys in Shared) |
| Flags | Auth change: password replaced, all sessions ended |
| DoD | Tests written and passing · only the given user's password and tokens change (another user's tokens stay active) · no password in logs or responses · build green |
| Depends on | T4, T5, T7 |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | Give `ChangePasswordRequest` `[Required]` and a max length on `CurrentPassword` and `[PasswordRules]` on `NewPassword`, so #24 passes for change |

| 3 | Wrong current password (`PasswordVerifier.Verify`) → 400 with a clear message; new password equal to the current one → 400, so #29 and #30 pass |
| 4 | On success, in one transaction: new BCrypt hash and all refresh tokens revoked with `password_changed`; then `IPasswordAuditRecorder.RecordAsync(userId, AuditActions.PasswordChanged)`, so #31–#33 pass |

**Delivered:** `PasswordChangeService.ChangePasswordAsync` implemented as guided (401 using existing `UnauthorizedMessage` key for unknown/inactive/unverified; 400 for wrong or identical password; hash replace and `password_changed` revocation in one transaction, then audit). A wrong current password does not count toward login lockout. `ChangePasswordRequest` got `[Required]`, max length 128 on the current password and `[PasswordRules]` on the new one. Added keys `CurrentPasswordIncorrect`, `NewPasswordSameAsCurrent`, `PasswordChangeSucceeded` to both resource files. No differences from the plan.
