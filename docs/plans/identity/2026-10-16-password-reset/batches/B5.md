## T7 — Reset the password with a code
| Field | Value |
|---|---|
| Expected context | `VerificationService.VerifyEmailAsync` checks the newest unused, unexpired code and counts failures with lockout from `MaxVerificationAttempts` and `VerificationLockoutDurationMinutes`. `IRefreshTokenService.RevokeAllForUserAsync` revokes every token of a user. Passwords are hashed with BCrypt as in `RegistrationService` |
| Expected result | Reset method on `PasswordResetService` taking email, code and new password (T4 rules). Unknown email, wrong, used or expired code, and a reset-locked user all get one generic rejection; wrong codes count toward the reset lockout, which invalidates the code at the limit. On success, in one Identity transaction: new password hash, code marked used, reset and login counters cleared, all refresh tokens revoked with a new `password_changed` reason. Then T5 records the audit entry |
| Outcome | #2, #3, #4, #7, #9, #11 — verified by unit tests: new password verifies and old does not, second use of a code fails, expired, wrong and over-attempted codes leave the hash unchanged, weak password refused, every refresh token revoked, audit recorder called once |
| Files | `change` `src/RestaurantManagement.Modules.Identity/Services/IPasswordResetService.cs`, `PasswordResetService.cs` · `add` `Models/ResetPasswordRequest.cs` · `change` `Entities/RefreshToken.cs` (reason constant), `Services/RefreshTokenService.cs`, `IRefreshTokenService.cs` (reason parameter) · `change` resource files · `add` `tests/RestaurantManagement.Modules.Identity.Tests/PasswordResetServiceResetTests.cs` |

| DoD | Tests written and passing · password and code never in logs or responses · failure leaves password and tokens unchanged · logout-all keeps its existing reason · build green |
