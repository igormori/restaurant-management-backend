## T2 — Verification code hasher
| Field | Value |
|---|---|
| Expected context | Identity services depend on interfaces (SOLID: Single responsibility, Open/closed, Liskov substitution, Interface segregation, Dependency inversion). No hashing helper for codes exists yet. Passwords use BCrypt, which is too slow and unsuitable for this job. Use `System.Security.Cryptography` only |
| Expected result | An `IVerificationCodeHasher` interface and its implementation in Identity `Services/`. It has two operations: compute the fingerprint of a code for a user, and check whether a submitted code matches a stored fingerprint. The fingerprint is HMAC-SHA256, keyed with `VerificationCode:HashKey`, over the user ID and the code, and stored as a lowercase hex string. Matching recomputes the fingerprint and compares the two with `CryptographicOperations.FixedTimeEquals`. An empty or malformed stored value never matches and never throws. The hasher is registered in `Program.cs` |
| Outcome | Supports #1 (fingerprint differs from the code), #2 (same code and user match) and #3 (wrong code does not match). Verified by unit tests |
| Files | `add` src/RestaurantManagement.Modules.Identity/Services/IVerificationCodeHasher.cs · `add` src/RestaurantManagement.Modules.Identity/Services/VerificationCodeHasher.cs · `change` src/RestaurantManagement.Web/Program.cs · `add` tests/RestaurantManagement.Modules.Identity.Tests/VerificationCodeHasherTests.cs |
| Modules | Identity (and one registration line in Web) |
| Flags | Security: cryptography; constant-time comparison is required (spec Rule 2) |
| DoD | Tests written and passing · the fingerprint is not equal to the code and does not contain it · the same code and user give a match · a wrong code gives no match · the same code for another user gives no match · a different key gives no match · an empty stored value gives no match · `dotnet build` and `dotnet test` green |
| Depends on | T1 |
| Uses from dependency | `IOptions<VerificationCodeOptions>.HashKey` |
| Provides | `IVerificationCodeHasher`, registered for dependency injection |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | Implement the stub `VerificationCodeHasher` in Identity `Services/`: keep the key from `IOptions<VerificationCodeOptions>` in the constructor; `ComputeHash(userId, code)` returns lowercase hex HMAC-SHA256 over the user ID and the code (scenarios #16–#18) |
| 2 | Implement `IsMatch(userId, code, storedHash)`: recompute and compare with `CryptographicOperations.FixedTimeEquals`; an empty, wrong-length or non-hex stored value returns false without throwing (scenarios #11–#15) |
| 3 | Register `IVerificationCodeHasher` in `Program.cs` next to the other Identity services (scenario #19) |

- **Tests to make pass, in order:** #11–#18 (`VerificationCodeHasherTests`), then #19 (`Startup_DefaultConfiguration_RegistersVerificationCodeHasher`)
- **Stubs created:** `src/RestaurantManagement.Modules.Identity/Services/IVerificationCodeHasher.cs` — interface with `string ComputeHash(Guid userId, string code)` and `bool IsMatch(Guid userId, string code, string storedHash)` (complete) · `src/RestaurantManagement.Modules.Identity/Services/VerificationCodeHasher.cs` — constructor takes `IOptions<VerificationCodeOptions>`; both methods throw `NotImplementedException`
- **Follow this existing pattern:** services depend on interfaces, like `IVerificationService`/`VerificationService`; registration style in `Program.cs` "Identity Module Services"
- **Watch out for:** keep the method names and signatures: the T3 and T4 tests call them directly. The constructor must not throw for a valid key, because the Identity test helper `TestVerificationCodeHasher` (in `IdentityTestDatabase.cs`) builds the real hasher. Include the user ID in the HMAC input with a clear separator so user and code cannot run into each other. Never log the code or the key

**Delivered:** Implemented `VerificationCodeHasher` (HMAC-SHA256 over `"{userId:D}:{code}"`, lowercase hex, `FixedTimeEquals`; empty or non-hex stored value returns false). Registered as a singleton in `Program.cs` under "Identity Module Services" (it holds only the key, so no per-request state). No differences from the plan. Remaining suite failures are T3/T4 tests.
