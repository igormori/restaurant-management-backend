## T1 — Verification hash key configuration and startup check
| Field | Value |
|---|---|
| Expected context | Options classes and validators live in `src/RestaurantManagement.Shared/Options/`. Follow `JwtOptions` and `JwtOptionsValidator`, which are registered in `Program.cs` with `ValidateOnStart`. `appsettings.json` commits a placeholder JWT (JSON Web Token) key, but Rule 7 forbids that for this secret. The EF (Entity Framework) migration bundles in Docker boot the Web host, so this startup check also runs in the `migrate` service. There are three places to supply the key. Docker reads `VERIFICATION_CODE_HASH_KEY` from `infra/docker/.env`. `dotnet run` uses user-secrets (`VerificationCode:HashKey`); `Web.csproj` has no `UserSecretsId` yet. Deployed environments use the Key Vault secret `VerificationCode--HashKey` |
| Expected result | A new options class (section `VerificationCode`, property `HashKey`) and its validator. The app refuses to start, with an error that names `VerificationCode:HashKey`, when the key is missing, empty or shorter than 32 bytes (UTF-8). This applies in every environment. `appsettings.json` holds an empty value and a `//` note listing the three ways to supply the key. `AuthApiFactory` supplies a test key so that existing Web tests still start. Infra docs and the env template list the new key |
| Outcome | #8: tested by starting the app without the key or with a short key (startup fails and names the key), and with a valid key (startup succeeds) |
