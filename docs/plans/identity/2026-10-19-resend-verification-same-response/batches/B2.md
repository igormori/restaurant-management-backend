## T3 — Resend only queues and always returns the same acknowledgement
| Field | Value |
|---|---|
| Expected context | `VerificationService.ResendVerificationCodeAsync` reads the user and codes, creates the code, sends the email in the request, returns `VerificationCodeResent` only for an eligible account and throws 500 `EmailSendingFailed` when sending fails. `PasswordResetService.RequestResetCodeAsync` is the pattern: it only adds a queue row and returns one acknowledgement. Module `CLAUDE.md` lines on the deliberate register/resend asymmetry become wrong |
| Expected result | Resend adds one verification row to the queue for whatever email is typed and returns 200 with `VerificationResendAcknowledged`, for every email and account state. Rate limit (429 Too Many Requests) unchanged. `VerifyEmailAsync` unchanged |
| Outcome | #1: unknown, verified, locked, within-wait and eligible emails get the same status and body (endpoint test). #2: the service has no email service, and with a failing email service the endpoint answer is unchanged. #3: known and unknown email run the same database commands (proof used instead of wall-clock timing, as in P20). #7: RS1 to RS6 rewritten for the new behaviour, each naming a passing test |
