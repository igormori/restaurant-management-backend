## T2 — Verification email processor
| Field | Value |
|---|---|
| Expected context | `PasswordResetEmailProcessor` is the pattern: claim each due row with a conditional update, read it again, check eligibility at the time the row is handled, store the code fingerprint, send, delete on success, retry after 1, 2, 4, 8 minutes, mark failed after the 5th failure, drop a row claimed again with its code already issued (at most one email after a crash), purge failed rows after 7 days. `VerificationService.ResendVerificationCodeAsync` holds today's eligibility and code rules |
| Expected result | A new verification email processor handles due verification rows the same way. Eligible account (spec Rule 5): older unused codes cancelled, new 6-digit code from `RandomNumberGenerator` stored only as its keyed fingerprint, verification failed-attempt counter and expired lock cleared, one verification email sent with first name and expiry, row removed. Unknown, verified, verification-locked or within-wait email: no code, no email, row removed. A retry skips the 60-second wait (its own failed code would block it). Send failure: row kept for retry; the log names the user ID, never the email address or the code. The existing email worker runs both processors each pass, and a failure in one does not stop the other |
| Outcome | #4: a simulated send failure is followed by a later pass that sends. #5: an eligible account gets exactly one email and its code verifies the account. #6: unknown, verified, locked and within-wait emails get no email. Verified by processor unit tests and one Web.Tests endpoint test (queued verification row, processor pass, code verifies) |
