## T1 — Per-address and whole-account login lock
| Field | Value |
|---|---|
| Expected context | `SessionService.LoginAsync` keeps one counter per account (`User.FailedAttempts`): 5 wrong passwords set `User.LockedUntil` for 15 min for everyone. Refused logins all throw the same 401 `InvalidEmailOrPassword`; unknown emails verify a dummy hash (keep it). Login already receives the client IP (Internet Protocol) address in `ClientInfo.IpAddress` from `RefreshTokenCookie.ClientOf`, read after `UseForwardedHeaders`, which `AuthRateLimitingExtensions` restricts to `AuthRateLimit:TrustedProxies`: the same source as rate limiting (Rule 8, no new address logic). `RefreshTokenAsync` and `SelectOrganizationAsync` refuse `User.LockedUntil`; `PasswordResetService` clears `FailedAttempts`/`LockedUntil`. Eight test files build `SessionService` directly: create the new lockout class inside `SessionService` the way `OrganizationMembership` is created (from the DbContext and options, optional `TimeProvider`), so its constructor stays compatible. Tests that read `User.FailedAttempts` (rows L4, L7, L8, C3, P10, R15) move to the new rows |
| Expected result | Wrong passwords are stored as rows in a new `login_failures` table (user, IP address, failed at, "counts for address", "counts for account", address lock end). A missing address is stored as `unknown`. Per address: the 5th counted wrong password for an account from one address sets an address lock of 15 min on that row and stops the earlier rows counting for that address; other addresses still sign in (Rule 1). Per account: the 20th counted wrong password within 60 min, from any mix of addresses (one address adds at most `MaxFailedLoginAttempts` = 5 to the account count in the window, however often its address lock expires and it tries again, so a lock needs at least 4 addresses), sets `User.LockedUntil` to 15 min through a conditional update (only when not already locked, so one request wins) and stops every row counting for the account (Rule 2). While either lock applies, nothing is counted or extended, and a correct password is refused (Rule 4). A correct password stops the rows of that account and address counting for the address; the account count is untouched and ages out of the window (Rule 5). Rows older than the window with no running address lock are deleted when a new failure is stored. Every refusal keeps the same 401 body (Rule 3). Both locks send the existing Sentry `AccountLocked` event with the user ID only (no email, no address). Password reset deletes the user's `login_failures` rows and clears `LockedUntil`. `users.failed_attempts` is dropped. Settings: `Security:MaxFailedLoginAttempts` (5) now counts per address; new `Security:AccountMaxFailedLoginAttempts` (20) and `Security:AccountFailedLoginWindowMinutes` (60); `LockoutDurationMinutes` (15) applies to both locks |
| Outcome | #1, #2, #3, #5 (unit and endpoint tests below); #6 (endpoint test: `X-Forwarded-For` from an untrusted sender ignored, from a trusted proxy used); #7 (shipped values test T16 reads 5, 20 per 60 min and 15 min from `appsettings.json`) |
