## T3 — Location time zone, type and code
| Field | Value |
|---|---|
| Expected context | `Location` (tenant entity, filtered by the token's organization) has no time zone, type or code. `LocationService` creates and edits locations for Owner or Admin only (role-name check, keep as is) and maps with `MapToResponse`. Another organization's location already returns 404 on edit. Delete is a soft delete (Status Closed), so closed locations keep their row and code. Enums bind as strings but also accept numbers and undefined values. Existing tests and seed helpers that create locations must set time zone and code (tester updates them before Gate 2). |
| Expected result | Create and edit require `timeZone`: a valid IANA (Internet Assigned Numbers Authority) name such as `America/Sao_Paulo`, `America/Toronto`, `America/New_York`; missing, unknown or Windows-style names (e.g. `E. South America Standard Time`) return 400. `type` is `Store` or `CentralKitchen`; when omitted it is `Store`; unknown or numeric values return 400. `code` is required, trimmed, stored uppercase, letters and digits only, up to 10 characters. A code already used by another location of the same organization (closed ones included, compared case-insensitively) returns 400 with a validation message; another organization may use the same code. A PostgreSQL unique index on organization and code backs the check, and a race that hits the index also returns 400, never 500. Responses include all three fields. |
| Outcome | #2 — create without time zone, and with `America/Curitiba_Centro`, return 400. #3 — create without type returns `Store`. #4 — a second `MM` in Org A returns 400. #5 — `MM` in Org B returns 200. |

South America Standard Time"), which must be rejected (scenario 11), so check the name is an IANA id. The uniqueness check is per organization: Trattoria may reuse Cantina's code (scenario 16).
