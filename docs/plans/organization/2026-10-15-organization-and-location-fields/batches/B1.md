## T1 — Organization currency
| Field | Value |
|---|---|
| Expected context | `Organization` has no currency. `CreateOrganizationAsync` builds the entity and response by hand; `GetOrganizationsAsync` projects the response in a query. Enums are sent as strings (`JsonStringEnumConverter` in `Program.cs`), but that converter also accepts numbers and undefined values, and a missing non-nullable enum binds to its first value, so a plain enum property would silently give a default currency. Existing tests and seed helpers that create organizations must send or set a currency (tester updates them before Gate 2). |
| Expected result | Create requires `currency` = `BRL`, `USD` or `CAD`; missing, unknown or numeric values return 400 with a validation message. Currency is stored as its text code and returned by create, edit and list. Confirmed by the user at Gate 1 (2026-10-15): currency is set per organization at creation and can never be changed, so the edit request has no currency field. No default exists anywhere. |
| Outcome | #1 — create without currency, and with `EUR`, both return 400 and store nothing; create with `CAD` returns it in the response. |
| Files | `add` currency enum in `Entities/` · `change` `Entities/Organization.cs`, `Models/CreateOrganizationRequest.cs`, `Models/OrganizationResponse.cs`, `Services/OrganizationService.cs`, `Data/OrganizationDbContext.cs` (text column, max 3) · `add` migration in `Migrations/` |
| Modules | Organization |
| Flags | Create-organization contract change; migration adding a required column (no data) |
| DoD | Tests written and passing · validation tests (missing, unknown, numeric) in `tests/RestaurantManagement.Modules.Organization.Tests` · endpoint test in `tests/RestaurantManagement.Web.Tests` showing currency stored and returned on PostgreSQL · an edit leaves the stored currency unchanged · `GET api/organizations` returns only the caller's organizations with their own currency (cross-tenant) · build green |
| Depends on | — |
| Uses from dependency | — |
| Provides | Currency on the organization and its responses; mapping points T2 extends |

| Step | What to do |
|---|---|
| 1 | Add validation to the `Currency` stub on `CreateOrganizationRequest` (required; only `BRL`, `USD`, `CAD`) so scenario 1 passes. Keep the request property as text: a JSON number then fails binding with 400 (guard scenario 23) |

Create, edit and list responses return the currency; edit never touches it. No difference from the plan.

## T2 — Settings: service charge, discount limit, cutoff
| Field | Value |
|---|---|
| Expected context | `OrganizationSettings` holds plan and trial fields only; it is created with the organization and has no endpoint of its own. `EditOrganizationAsync` already allows only Owner or Admin of the token's organization (role-name check, keep as is). Plan and trial fields stay unchanged. |
| Expected result | Settings gain service charge rate (default 0), discount approval limit (a percentage, default 0) and business-day cutoff (default 04:00). Create always sets these defaults. `PUT api/organizations/edit` requires all three: rates are 0 to 100 with up to 2 decimals, cutoff is a time of day sent and returned as `HH:mm`. Out-of-range or malformed values return 400 with a validation message and change nothing. Create, edit and list responses include all three. |
| Outcome | #3 — a new organization returns service charge 0, discount limit 0, cutoff `04:00`. #6 — edit with service charge 120 (also -1, and discount limit 120) returns 400. |
| Files | `change` `Entities/OrganizationSettings.cs`, `Models/EditOrganizationRequest.cs`, `Models/OrganizationResponse.cs`, `Services/OrganizationService.cs`, `Data/OrganizationDbContext.cs` (numeric precision 5,2) · `add` migration in `Migrations/` |
| Modules | Organization |
| Flags | Edit-organization contract change; migration on the settings table (no data) |
| DoD | Tests written and passing · service tests for defaults and each range limit (0 and 100 accepted, -1 and 120 rejected) · endpoint test on PostgreSQL that an edit stores the values · cross-tenant: an edit body naming another organization changes only the token's organization, the other stays untouched · one rejection test each for Manager, Cashier, Waiter and Kitchen (403, nothing changed) · build green |
| Depends on | T1 |
| Uses from dependency | Updated organization response mapping and create flow |
| Provides | `BusinessDayCutoff` (time of day) on settings, used with T4 in Phase 1 |

**Implementation guide** (written by the tester)
| Step | What to do |
|---|---|
| 1 | Add validation to the three stubs on `EditOrganizationRequest`: all required; `ServiceChargeRate` and `DiscountApprovalLimit` 0 to 100 with at most 2 decimals; `BusinessDayCutoff` exactly `HH:mm` (00:00–23:59). Scenarios 6 and 7 |
| 2 | Add `ServiceChargeRate` and `DiscountApprovalLimit` (decimal, precision 5,2) and `BusinessDayCutoff` (time of day) to `OrganizationSettings`; generate the migration |
| 3 | In `CreateOrganizationAsync`, set 0, 0 and 04:00 on the new settings and save them; fill the three response fields (cutoff formatted `HH:mm`) in create, edit and the list projection. Scenario 8 reads the stored values back through `GetOrganizationsAsync` |
| 4 | In `EditOrganizationAsync`, save the three values on the token organization's settings only (scenarios 9, 10) |

- **Tests to make pass, in order:** 6, 7 (guard, keep green), 8, 9, 10
- **Stubs created:** `Models/EditOrganizationRequest.cs` — `ServiceChargeRate`, `DiscountApprovalLimit`, `BusinessDayCutoff` · `Models/OrganizationResponse.cs` — the same three fields (cutoff as text)
- **Follow this existing pattern:** the `RegularExpression` attributes on the colour fields for the cutoff format; `EditOrganizationAsync` already loads the settings and checks the role
- **Watch out for:** each invalid case must flag only its own field (scenario 6 checks the exact field). Keep the Owner/Admin role check and plan/trial fields unchanged. The cutoff is returned as `05:30`, not `05:30:00`

**Delivered:** `OrganizationSettings` gained service charge rate, discount approval limit (numeric 5,2) and business-day cutoff (`TimeOnly`, default 04:00); migration `AddOrganizationSettingsFields`. `EditOrganizationRequest` validates all three (Required, Range 0-100, `IValidatableObject` for the 2-decimal limit, `HH:mm` regex). Edit saves them on the token organization's settings. Difference: the create, edit and list mappings now share one private `ToResponse` helper in `OrganizationService`, and the list loads entities then maps in memory (a `TimeOnly` cannot be formatted in the SQL query).
