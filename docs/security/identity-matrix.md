# Identity security matrix

The record of every rule the Identity module must keep, on the security and the behaviour side,
and the test that proves each one. The pipeline (`.github/workflows/dotnet.yml`) runs on every
pull request and every push to `main`. It runs every test named here, and
`.claude/scripts/check-security-matrices.py` fails the build when this file and the tests drift
apart: a named test that no longer exists, an Identity test mapped nowhere, or a ✅ row with no
test.

## Rules for this file
- Any change to Identity updates this file in the same change: new rows for new behaviour,
  changed rows for changed behaviour, and the test that covers each.
- A new feature that touches authentication adds its security cases here (status ❌) before it
  is built. The rows turn ✅ only when their tests pass.
- No row is ✅ without a named test. Name tests as `ClassName.MethodName`.
- Every Identity test is named in a row, or in section 11 when it protects the schema or wiring
  rather than a rule.
- Every named test carries `[Trait("Rule", "<ID>")]` for each row naming it, and its key
  assertions say the rule in plain words. In CI a failure is reported as "Rule L8: 5th wrong
  password", with the Expected column and the failure message, on the run page and the pull
  request. Run one rule locally with `dotnet test --filter Rule=L8`.
- Row IDs never change or get reused. A removed rule is deleted with its row.
- The pull request reviewer checks every Identity change against this file and flags anything
  missing.

**Status:** ✅ covered by the named test · ❌ no test yet · 🐞 known bug, see the backlog item

**Where the tests live:** unit tests in `tests/RestaurantManagement.Modules.Identity.Tests/`,
endpoint and database tests in `tests/RestaurantManagement.Web.Tests/Identity/`. Exceptions in
Web.Tests outside that folder: `PrivateByDefaultTests`, `StartupConfigurationTests`,
`RequiredIdFieldEndpointTests` (they cover several modules).

**Limits in force (`appsettings.json`, guarded by T16–T18 so changing a number fails a test;
environment variables set at deployment can still override them):** 5 wrong logins lock login for 15 min · 5 wrong codes
lock verification, or reset, for 15 min · codes are 6 digits and expire after 10 min · 60 s
between resends · access token 15 min · refresh token 30 days · rate limits per IP address:
login 10/min, register 5/h, verify 10/10 min, resend 3/10 min, refresh and logout 30/min,
forgot password 3/10 min, reset password 10/10 min, change password 10/min. Access tokens get no
grace past expiry (T15).

**Accepted ASVS 5.0 deviations (decided 2026-10-16, see `identity-asvs-gap-report.md`):**
passwords keep the uppercase, digit and symbol rule (R7, R8; ASVS V6.2.5) · no list of a user's
sessions: logout-all is enough (O5; ASVS V7.5.2) · passwords over 72 bytes are refused, so 64
accented or non-Latin characters may not fit (R6, T7; bcrypt limit, ASVS V6.2.9).
